# 工作流与决策

## 索引

| ID | 关注点 | 静态证据能说明什么 |
|---|---|---|
| C03 | 开工前未对齐 | 任务是否有目标、边界和验收 |
| C04 | 对齐过频/过重 | 流程是否强制无差别审批；实际阻塞需会话证据 |
| C08 | 未复盘历史会话 | 是否存在证据到改进的路径；习惯需历史证据 |
| C09 | 过多人工审查 | 是否把可确定检查留给人；实际负担需样本 |
| C10 | 没有用原型化解未知 | 是否有适合实验的问题；不要求原型配额 |
| C12 | 过度人工看管 | 是否缺少有界自主工作与异常升级机制 |
| C15 | 缺乏共享术语 | 需求、代码、测试是否存在具体语义冲突 |
| C17 | 缺乏策略性规划 | 目标、依赖、风险和阶段验收是否可追溯 |
| C18 | 缺少必要思考/验证 | 是否缺少可观察的假设、反例与决策依据 |

这些检查评估可观察机制，不评价用户是否“聪明”“够不够努力”。日志不在范围内或信息不足，就保留未知。不会因为某个文档名字不存在而生成缺陷。

## 行为取样规则

只有当前项目、明确授权范围内的历史可用。有时间窗口时优先取最近 3–5 次可用会话，并注明数量；允许用失败、正常、关键变更样本补充，但要标为目的性抽样。区分用户确认、工具权限弹窗、真实业务决策、重复提醒及可独立解决的阻塞。

每个事件引用原始会话 ID/事件 ID或时间；摘要只能作为线索。不要把压缩摘要当完整记录，不跨项目搜集用户画像，不引用其他项目私密内容。样本少只能描述本样本，不报总体百分比或长期趋势。

## C03 开工前对齐

寻找目标、非目标、约束、不变量、验收条件、依赖和待决问题是否能直接交给实现者。文档不必叫 PRD/spec/ticket；已有 Issue、对话中的明确契约也有效。

反证：小改动有清晰上下文时，强制再写一套方案是浪费。方案文件不存在不等于没对齐。

最小方案：只补影响正确性或不可逆选择的缺口；一次确认必要决定，不重问已经有据可查的问题。验收是 agent 能准确复述交付边界并知道如何验证，不是文档变长。

## C04 对齐过频/过重

从流程或会话找同一决定多次确认、低风险细节反复审批、一次简单改动走完整大型设计流程、实现与计划之间无信息增量的往返。没有行为证据时不声称实际浪费时间。

反证：生产、权限、隐私、真实资金、不可逆变更和需求变动需要确认；频繁失败可能说明上游定义不足，而非用户控制过多。

最小方案：按风险设决策节点，复用已确认决定与变更记录。去掉重复确认，不去掉安全授权。不得通过扩大默认写权限来“优化对齐”。

## C08 会话复盘与学习闭环

寻找一次真实失误/卡点能否关联到定位指针、自动检查、评审准则、工具修正或其他机制，再关联到后续类似任务的结果。只存在记忆笔记但没有作用路径，不证明已经改进。

反证：简单顺利会话不一定值得复盘；没有 `retro` skill 不代表没有复盘；偶发事故不一定需要永久规则。

最小方案：针对重复或高代价事件做证据驱动复盘，复用既有改进清单；记录本次最小改进的验收点与复查时机，不把每次会话都变成新增规章。只提出候选，不调用会写文件的复盘/记忆工具。

## C09 人工审查与风险分工

查哪些人工动作是纯机械的格式/类型/已定义规则检查，哪些是产品判断、业务不变量、资金/权限边界、发布决定。只有在存在可靠的替代反馈与适当权限边界时，才讨论减少低风险重复检查。

反证：高风险系统保留人工审查是合理设计；自动 review 存在不代表可靠；测试全绿不等于业务正确。

最小方案：把机械检查交给已有工具，给审查者可追溯的变更摘要、原始证据与高风险清单；人工继续负责有判断价值的环节。不要建议用户完全不看关键 diff，不承诺“全自动后无人负责”。

## C10 用原型化解不确定性

寻找长时间语言讨论仍解决不了的 UI 交互、外部接口能力、性能可行性或复杂业务理解差异。说明需要验证的具体假设、结果如何改变决策以及实验成本。

反证：普通修复、已知约束、需要严谨保证的生产路径不一定适合原型；没有 prototype 目录不是问题。

最小方案：提出隔离、可丢弃、有时间与费用上限的实验，预先明确成功/失败标准，不接真实资金或生产系统。本次不生成、不运行原型。原型验证未知，不替代已经承诺的完整系统功能与最终交付范围。

## C12 有界自主工作与人工看管

从会话识别 agent 等待重复指令、不会读取已有失败证据、无完成/停止条件、错误后无界重试、只报“好了”不报结果等问题；也检查任务是否大到无法在一个上下文中有效完成。

反证：权限弹窗可能是正确边界；频繁人工干预可能来自工具缺失、需求变化或真实业务危险，不是 agent 需要更多自由。

最小方案：补有界任务包：目标、允许动作、预算、完成证据、异常升级点、停止条件。给 agent 必要的只读可观测性，而不是生产写权限。不得以减少看管为理由自动启用 auto/full-access/危险跳过权限模式。

## C15 共享语言

抽样对照需求、接口、类型、测试、日志与已有术语说明，找同一个词是否混指不同实体、状态或事件，或者多个词是否造成具体误解。必须展示冲突与影响路径。

反证：词汇不同可能来自上下文边界；一个项目没有 GLOSSARY.md 不等于缺共享语言；不强制采用外部作者的词汇禁用清单。

最小方案：在既有规范或靠近契约的位置定义少量歧义词、边界及例子；先不批量改名。改代码名称属于独立整改，需迁移兼容和测试验收。

## C17 策略、依赖与交付顺序

检查研究/实现活动是否关联用户目标、依赖、风险消减与阶段验收；是否在核心路径未验证时优先优化次要模块；是否重复选择互不兼容的方案。

反证：按依赖分批施工不等于缩减最终范围；探索性研发不一定有固定 roadmap；实验失败可能提供必要信息。

最小方案：明确关键依赖和“下一步最需要消除的风险”，给分批实施顺序和验收；不是替用户改产品目标，也不是建议把完整平台变成几个孤立功能。

## C18 决策、反例与验证

只评估可观察产物：重要假设是否声明，备选方案是否有取舍，是否回查原始资料，关键判断是否考虑反例，结论是否有完成证据。不要索取、推断或评判隐藏思维链。

反证：回答简洁、推理不可见、没有长计划，不证明“没有思考”；一个小任务可以用很少文字作出充分决策。

最小方案：在高风险决定处加入假设、最短反证路径和停止条件；低风险路径保持简单。不要一律调高 effort，也不要增加只会复述结论的审查轮数。
