# 优先级、证据与最小整改

## 先分类，不先打分

`AD-*` 是在明确范围内有证据支持的问题；`VFY-*` 是需要补证或受控实验的任务。不要把“未访问”“没运行”记为缺陷，不把“没有某个文件/skill”记为功能缺失。

证据等级与置信度分开写：静态证据可以高置信证明某条失败码被吞掉，但不能高置信证明生产事故已经发生。用户陈述可以证明用户感受或要求，不自动证明底层配置原因。旧记录只证明对应时间/ref 的行为。

每个候选的最小证据包：
- 可观察事实及原始定位；明确不是作者观点或一般最佳实践。
- 从事实到用户影响的因果链，以及链条中尚未核实的部分。
- 已尝试的反证、替代解释与不适用边界。
- 证据来源类型、时效与当前 revision/配置关联。

不要要求输出内部思维链。报告只给可检查依据、结论和不确定性。

## 第一性原理与减熵门

顺序固定：需求/不变量 → 当前机制 → 缺口/反例 → 最小充分修复 → 根因去重 → 定级。

删除规则、测试、文档、hook 或抽象前，必须回答它原先保护什么、谁仍依赖它、是否存在独立约束、由什么保留机制接管、如何验证没有退化。无法排除独立用途时，只给调查/迁移方案。

优化建议必须有可观察收益路径。单纯“不符合某位作者的推荐”不是缺陷；不能把业务必需复杂度当技术债。新增任何组件都要说明为什么现有组件接通/调整不能解决。

## 根因去重

同一有效来源中的错误指令让多个 skill 出错，可合并为一个问题，并列所有受影响对象。没有共同证据与同一修复机制时，不为了少写卡片硬合并。

同一个主题下可以有不同根因：没有测试、测试未接入、测试不检验行为是三种问题，不能都写成“测试不足”。独立验收或不同授权范围的整改可成为同一根因下的子任务。

## P0–P3

| 优先级 | 条件 | 典型整改目标 |
|---|---|---|
| P0 | 有可信证据说明重大破坏正在发生或迫近；例如已知自动动作将碰生产/外泄敏感数据 | 先向用户明确风险和需批准的止损动作；审计者不自行止损 |
| P1 | 已证实关键正确性缺口、关键门禁无效，或反复阻塞正常交付 | 恢复可靠验证、解决配置冲突、打通关键反馈 |
| P2 | 有证据的反复探索、上下文膨胀、低价值等待或工具返回浪费 | 降低重复成本，不削弱正确性与安全 |
| P3 | 可选便利、低频问题、收益较小的整理 | 用户按时间与维护预算选择，可不做 |

优先级按本项目影响与触发路径决定，不为某个 Cxx 固定等级。“没有自动 review”不天然是 P1；长文件不天然是 P2；严重猜测不能装作已确认 P0。

关键安全事实未知时，可以把补证设为 P1，明确这是验证紧迫度并建议在未知消除前不要执行相关高风险动作。这是行动建议，不是假称已经检测到事故。

## 同级排序与执行依赖

同级依次考虑影响范围、重复频率、阻塞程度、证据确定度、修复投入与变更风险。默认用高/中/低与具体依据，不捏造精确 ROI 或总健康分。

执行顺序另外列依赖图：先隔离/补证与恢复验证，再做安全的上下文或工具优化，最后做结构性重构。P2 若是 P1 的必要前置，可先执行该最小前置，但保留其实际优先级与理由。独立的急迫止损建议不应被文档整理阻塞。

估算使用 S/M/L 并解释拆改面：S 为少量入口/配置，M 为跨文件但局部，L 为跨模块/工具链。时间与费用只有有依据时才给区间；没有基线时写未知。

## 整改放在哪里

| 根因 | 优先选择 | 避免 |
|---|---|---|
| 机械规则无落实 | 复用/接通检查，必要时增加最少断言 | 在全局 prompt 重复强调 |
| 判断性标准不清 | 明确契约或定向审查准则 | 伪装成确定性测试或无限加 review |
| 信息找不到 | 修复现有导航/证据读取路径 | 写整本全仓说明书 |
| 实际常驻内容过多 | 条件加载、去重、修复触发 | 只看文件大小，盲删安全要求 |
| 工具结果低效 | 参数过滤、分页、稳定证据定位 | 摘要替代原始证据或新装一堆工具 |
| 设计未知 | 提议隔离的小实验 | 未批准即做原型或缩减最终产品范围 |
| 权限/隔离缺口 | 提议最小权限与安全验收边界 | 审计者自行改全局权限 |

每项至少给最小方案、一个替代方案或明确“无合理替代”，以及不做的后果。整改不得仅写“优化 prompt”“加强测试”“完善架构”。
