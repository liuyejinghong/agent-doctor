# 验证与架构

## C05 自动检查：定义、接入、执行、效果分层

从任务入口追踪到实际命令定义、包含的检查、失败码、CI 触发条件、分支/路径过滤、`continue-on-error`、跳过规则和相关发布/合并门禁。只做静态阅读，不执行它们。

把证据分成四层：
1. 定义存在：有规则或脚本。
2. 已接入：工作流会调用，且失败未被明显吞掉。
3. 有运行记录：已授权的现成日志说明某个时间/ref 执行过什么。
4. 有效拦截：与目标不变量相关的已知错误曾被正确阻断，或未来受控测试将证明这一点。

CI YAML 无法单独证明远端分支保护/required checks 生效；读取不到服务端策略时标未知。旧版本的绿色记录不是当前工作树通过的证据。本地失败记录也要区分环境失败与真实产品缺陷。

反证：某些可选 job 合理允许失败；文档项目不必配齐所有语言检查；已有等效验证入口应承认。完整错误链只要被其他有效必需门禁拦住，就不能宣称必然能合并。

最小方案：优先接通已有检查、修复错误传播/作用域、给关键不变量补最少检查。避免添加重复 hook 与 CI 阶段；新门禁建议先验证误报和耗时，再逐步阻断。

验收方案：在隔离环境给代表性违规样本和合法样本，前者被适当阻断，后者通过；明确对应命令、目标 ref、网络与生成文件。本次不运行。

## C07 自动审查：判断不是确定性证明

阅读已有审查说明与可用样本，检查审查是否看到需求/不变量、变更、必要代码上下文和当前验证证据；是否主要照抄实现者总结；是否有逐项处置、反证与复核机制。

实现与审查上下文应分离：不给审查者先入为主的自我辩护，但保留判断所需的契约、代码与证据。不同模型可作为选项，不是必须；没有必要为了审计开启新模型。

反证：小型低风险改动可能无需多代理；高假阳性 review 比没有 review 更浪费；单纯增加审查次数不能证明收益。

最小方案：优先改善既有审查输入与问题处置；对已确认高风险变更设置针对性审查。对已装审查框架（包括 FSR 或等效机制）复用其能力，不重复部署第二套总审计器。

验收：用明确已知问题和干净变更的案例检查漏报、误报与复核成本；分别报告“实现是否满足要求”与“是否遵守必要标准”，不把一个维度的好表现抵消另一个维度的失败。

## C11 agent 自证能力

逐类确认完成证据是什么、如何取得、agent 是否有合法读取途径：单元/集成测试记录、UI 截图/状态、日志、服务响应、构建产物、数据库断言、领域模拟等。检查它能否区分“没法验证”与“已完成”。

本次只看已有资料。缺少浏览器/MCP 不自动是问题，要看任务是否真的需要；不要启动浏览器去证明能力，也不要请求生产凭据。

反证：命令不可读可能是本次审计权限不足，不是实现 agent 一直没有权限；不能把审计会话的限制当作被审计工作流的固有缺陷。

最小方案：优先连接既有结果与只读观测入口，建立按任务类型选择的验收配方。新增工具需要证明现有方法不足并说明权限、成本与维护影响。

## C16 架构与测试质量

按关键业务流抽样读取公共契约、实现、测试与 fixture。关注测试是否验证用户可观察行为/领域不变量，是否只重复实现、仅断言内部函数被调用，是否需要大量内部 mock 才能运行，是否错误路径/边界全部不可观察。

给具体的假设错误与测试失效机制；没有执行时称“静态可疑”并提出验证任务，不声称做过 mutation test。区分外部依赖隔离与内部实现耦合；mock 并非一律错误，集成测试也不是越多越好。

反证：覆盖率不能单独证明有效性；内部测试有时合理；纯接线代码不一定值得重复测试；失败可能来自测试设计而非必须重构架构。

最小方案：先修测试边界/fixture 或缺失断言。只有可证明结构让正确验证持续困难，且局部修正不足时，才建议抽出少量稳定边界；为每次重构写清不变量与兼容性。不要为了某个术语偏好全面重构。

## G04 验证环境与恢复

静态查看测试目标选择、防误连机制、模拟/生产配置分离、可观察结果和恢复方法；不打开秘密文件验证地址，不实际连接任何交易/资金/生产接口。

确认是否能在不触及真实资金/数据的情况下验证关键流程；“模拟环境”名称不构成隔离证据。查看默认目标和显式覆盖是否会越过边界。

反证：无法读取私有部署配置不等于没有隔离；不要把缺乏可见恢复文档直接等同不能恢复。

最小方案：提出明确隔离边界、必要的防误连断言与可控验收环境。涉及真实资金的系统不得通过下真实订单验收此 skill 或环境整改；普通公开策略/模拟输入能验证平台流程时，不以盈利作为工具链验收条件。

回滚也要具体：文件/配置恢复、临时产物清理与运行态影响分别说明；不可逆操作必须另行批准，不把“git revert”当作所有动作的通用回滚。
